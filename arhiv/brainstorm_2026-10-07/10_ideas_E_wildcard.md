# Lens E (cross-domain wildcard): four mechanism ideas

Scope: user-level pure ε-LDP, one report per user per collection window, untrusted server; output = edge sequences on the public Beijing graph plus departure time and per-edge travel times. `fit` groups the train views by `user_id`, runs the local step once per user with the generator's seeded RNG and aggregates; a membership-inference candidate thus enters a shadow as a one-trajectory user.

## Shared facts

- **One-report lemma.** If a user sends exactly one item through an ε-LDP randomiser (GRR, OUE/OLH, piecewise mechanism PM) and the item is any function of the user's whole data set, the report is user-level ε-LDP: the output distributions are mixtures over items and any two items have likelihood ratio ≤ e^ε. No composition. **Slot sampling** = a public, data-independent draw picks one slot of the user's statistic vector; only that slot is reported with the full ε. **Bounded contribution** = report shares or per-trip averages, which lie in a public interval whatever the trip count.
- **Noise.** Estimate variance from n_s reports: GRR over d values (d−2+e^ε)/(n_s(e^ε−1)²); OUE 4e^ε/(n_s(e^ε−1)²); PM on [−1,1] ≈ 3.7/n_s, 0.65/n_s, 0.085/n_s at ε = 1, 2, 4. So n = 182 with four slots (≈45 users each): GRR-4 std 0.19/0.07/0.02 and PM std 0.29/0.12/0.04 of the half-range at ε = 1/2/4; n = 10,000, OUE, ε = 1: std 0.019 per cell. Hence at n≈180 each design carries about five numbers at ε ≤ 2 and takes the rest from public road-graph priors via shrinkage; at n≈10,000 it carries 10²–10³.
- **Shared router (Boltzmann walk toward D).** From the head node of the current edge draw the next out-edge e′ ∝ exp(−β·(cost(e′) + V_D(head(e′)))), with V_D the public shortest-path length to D (one reverse Dijkstra, scipy.sparse.csgraph, cached per destination). Paths are road-valid by construction and their probability is an explicit product, which is `sequence_log_prob`; a public floor for non-adjacent consecutive edges keeps it finite for every sequence.

### Idea 1: Low-pass mobility field (graph-spectral LDP)
- **One-sentence pitch:** Estimate the population's visit density only through its low-frequency coefficients in the road graph's Laplacian eigenbasis, and the daily departure cycle through three Fourier harmonics, letting the exactly known LDP noise decide how many modes survive.
- **What each user computes locally:** v_u = distribution of the user's matched edge endpoints over the N≈35.8k nodes (a probability vector over all trips). c_{u,k} = Σ_i U_k(i)·v_u(i) for the first K eigenvectors U_k of the normalised Laplacian of the undirected road graph (public, cached); |c_{u,k}| ≤ b_k := max_i|U_k(i)| ≈ 3/√N. Time: per-trip means of cos and sin(2πm·t_dep/24 h), m = 1..3 (six values in [−1,1]). ℓ_u = mean capped length/30 km ∈ [0,1]; ρ_u = mean speed ÷ length-weighted maxspeed, clipped to [0,1.5]. Dimension d = K+8; K≈8 at n≈180, K≈200 at n≈10k (plus ρ per class × day period).
- **What is randomized and how:** Slot sampling (public weights may favour low modes); the user rescales x_{u,j} from its public interval to [−1,1] and sends PM_ε. One report, no budget split.
- **What the server does:** Unbiased slot means; spectral shrinkage ĉ_k ← ĉ_k·max(0, 1−σ_k²/ĉ_k²) with σ_k² known from the mechanism, so modes below noise vanish; f = Σ_k ĉ_k U_k clipped to ≥0 and renormalised; same for the 24 h density; gravity scale λ from ℓ̂.
- **How a synthetic trajectory is generated:** O ~ f; D ~ f(j)·exp(−d_sp(O,j)/λ̂); path = shared router with cost = length; departure ~ harmonic density; edge time = length/(ρ̂·maxspeed) + public turn delay. `sequence_log_prob` = log f(O) + log P(D|O) + Σ log steps.
- **Why it is user-level pure LDP:** One-report lemma on one bounded coordinate of a vector that is a deterministic function of all the user's trajectories; the slot draw is data-independent. Subtle: caps and b_k must be public constants; shrinkage and clipping are post-processing.
- **Expected behaviour at n~180 vs n~10,000:** Per-coordinate std = √(d·σ²_PM/n) of the half-range: n = 182, ε = 2, d = 16 gives 0.24, so K≈4–8 modes (centre–periphery plus two or three regional lobes), one harmonic and one speed scalar carry signal; at ε = 1 (0.57) only the first mode, i.e. the public density. n = 10k, ε = 1, d≈200 gives 0.27 before shrinkage, which keeps the few dozen modes above it. Degradation is automatic and the basis is nested: one code path for both rungs.
- **Closest existing work and what differs:** Graph-signal denoising (Shuman et al. 2013), central-DP wavelet/Fourier histograms, grid histograms in LDPTrace/RetraSyn. I know of no LDP mobility synthesiser using the road graph's spectral basis with noise-adaptive shrinkage; the novelty is the nested graph-aware parametrisation, not the primitive. If low eigenvectors localise on bridges or suburbs, swap to orthonormalised 2-D cosine modes on node coordinates; the mechanism is basis-agnostic.
- **Implementation effort:** M: scipy `eigsh` cached by map hash, projection, PM, shrinkage, shared router.
- **Main risk / failure mode:** The field says only *where*: routes are generic shortest-ish paths between density blobs, so cell-JSD may improve while route realism stays at Markov level; at ε ≤ 1, n≈180 the output is the public density.

### Idea 2: Part-of-speech trajectories (manoeuvre × road-class n-grams, grammar-constrained decoding)
- **One-sentence pitch:** Tag every move with a public "part of speech" (manoeuvre × road class), learn the population's token n-gram under LDP as a translation-invariant driving-style model, and generate by constrained decoding against the road graph, as language models decode against a grammar.
- **What each user computes locally:** Token of move e_{i−1}→e_i = manoeuvre from the public bearing change (straight/slight/left/right/U-turn) × class of e_i (motorway-trunk/primary/secondary/tertiary/residential-other), plus BOS and EOS: 27 tokens. q_u = the user's bigram distribution over 27² pairs (a probability vector whatever the trip count); departure-period shares (24); origin-zone shares (12×12); speed ratio per class ρ_{u,c} ∈ [0,1.5]. n≈180 alphabet: class unigram (5), manoeuvre unigram (3), one EOS hazard, one ρ, four periods.
- **What is randomized and how:** Slot sampling over bigram/origin/departure/speed with public weights (e.g. 0.4/0.3/0.2/0.1). Bigram: draw one move uniformly from the user's moves and report its pair with OUE_ε (GRR_ε on the reduced alphabet at n≈180); origin and departure: one sampled trip's item via OUE/GRR; speed: PM_ε. One report per user.
- **What the server does:** Debias, clip, renormalise; smooth the bigram toward the public prior = token bigram of a uniform random walk on the road graph (back-off to the "graph language"); keep the tilt r(tag′|tag) = P̂/P̂_prior.
- **How a synthetic trajectory is generated:** Origin edge from the origin histogram (public density at n≈180). At each head node tag every out-edge and draw one ∝ r(tag′|previous tag) × an optional pull exp(−β·Δ distance-to-go) toward a gravity-drawn destination; stop by the EOS hazard. Departure from the period histogram with a public within-period curve; edge time = length/(ρ̂_c·maxspeed) + manoeuvre delay (public constants, e.g. left turn 10 s). `sequence_log_prob` = log P(origin) + Σ log(r normalised over the out-edges actually available) + log hazard; no Dijkstra when the pull is off.
- **Why it is user-level pure LDP:** One-report lemma: one sampled item or one PM value per user with the full ε; the randomiser's guarantee holds for every input item, so how the move was sampled is irrelevant. Subtle: tokeniser and alphabet are fixed from the public map; the number of moves never leaves the device.
- **Expected behaviour at n~180 vs n~10,000:** n≈180: about 14 numbers over four slots, GRR-5 std ≈ 0.08 at ε = 2: a style summary (major versus minor roads, straight versus turning, trip length), nothing geographic beyond the prior. n≈10k: the 27² bigram at OUE std ≈ 0.03 (4,000 users on the slot) resolves the few dozen frequent pairs and impossible pairs clip to zero; 144-zone origin, 24 periods and five class speeds are usable.
- **Closest existing work and what differs:** Cunningham et al. (n-grams over spatial cells with reachability pruning), TrajLDP direction perturbation (per point), road-type transition priors in map-matching HMMs, driver identification from manoeuvre statistics. Difference: the alphabet is the move's part of speech, not a location, so the model is tiny and pools across the city; geography enters only through the public graph at decoding time. Honest doubt: a non-private road-class Markov generator may exist.
- **Implementation effort:** S–M: tokeniser from public geometry, OUE/GRR, constrained decoder.
- **Main risk / failure mode:** Pull off: walks wander and lengths are unrealistic; pull on: the n-gram adds little beyond the router. Origin–destination utility at n≈180 rests entirely on the public gravity prior.

### Idea 3: Revealed-preference moments calibrate a public route-choice and congestion simulator
- **One-sentence pitch:** Users report a few bounded statistics of their routes measured relative to the public shortest path; the server calibrates a recursive-logit-style route-choice model and a volume–delay timing model to reproduce them by simulation (simulated method of moments, as in traffic-simulator calibration).
- **What each user computes locally:** For each matched trip the device computes the public shortest path between the endpoints and averages differences over trips: detour ratio r_u ∈ [1,3]; class-share differences s_{u,c} = share of length on class c minus the shortest path's, ∈ [−1,1], five classes; turn density difference τ_u ∈ [−10,10]/km; speed ratio per day period ρ_{u,h} ∈ [0,1.5], four periods; mean capped length ℓ_u ∈ [0,30 km]; plus origin zone, destination zone and departure period of one random trip. 11 numeric + 3 categorical slots. n≈180: five slots (ℓ, r, major-road preference m_u = s_motorway + s_primary, one ρ, departure period); O/D from the public prior.
- **What is randomized and how:** Slot sampling with public weights; numeric slots PM_ε on the rescaled interval, categorical GRR_ε (OUE at n≈10k). One report per user.
- **What the server does:** Unbiased slot means with known covariance Σ̂. OD matrix = Furness/IPF balancing of the public gravity seed m_i·m_j·exp(−d_ij/λ̂) (zone mass = public road length) to the estimated origin and destination marginals (seed only at n≈180). Route model = shared router with local cost w_class(e′)·length + w_turn·turn(e′) and public length-based V_D, so Dijkstra trees never depend on θ = (β, w_class × 5, w_turn). Calibration: minimise (m(θ)−m̂)ᵀΣ̂⁻¹(m(θ)−m̂) + ridge toward θ₀ = pure shortest path, where m(θ) are the same moments from 2,000 trips simulated on cached trees; coordinate-wise search over ≤ 6 parameters, 10–20 s.
- **How a synthetic trajectory is generated:** (O,D) zones from the balanced matrix, nodes within zones by public road density; departure from the period estimate with a public within-period curve; route by the calibrated walk; edge time = length/(ρ̂_h·maxspeed) + turn delay. n≈10k extension: BPR volume–delay t = t₀·(1+α(x/κ)⁴) with x = synthetic flows scaled to a public city total and κ public class capacities, iterated to stochastic user equilibrium, so morning congestion emerges physically. `sequence_log_prob` = log P(O,D) + Σ log steps.
- **Why it is user-level pure LDP:** One-report lemma; every numeric slot is a per-trip average of a clipped quantity, so a user with 1 or 500 trips has the same domain. Subtle: the shortest-path baseline uses the public graph only; calibration and IPF are post-processing and may use Σ̂, a function of ε and n alone.
- **Expected behaviour at n~180 vs n~10,000:** n≈180, five slots, ε = 2: PM std 0.12 of the half-range, i.e. ℓ ± 1.8 km, detour ± 0.12, major-road preference ± 0.12: enough to tilt β and one class weight off θ₀; at ε = 1 the simulator is the public shortest-path model with an estimated mean length. n≈10k: all 14 slots, 12×12 OD by IPF from two 144-cell marginals (std 0.019), class weights, turn penalty and period speeds identified, BPR meaningful.
- **Closest existing work and what differs:** Recursive logit (Fosgerau, Frejinger & Karlström 2013); traffic-simulator calibration from trajectories (non-private, arXiv 2501.10934); central DP on Markov-chain traffic models (arXiv 2202.03325); SPRT's public geography; TS-TrajGen (A*, non-private); DP-Star/AdaTrace trip distributions (central). New: a user-level revealed-preference moment relative to a public baseline identifies a six-parameter simulator, a count n≈180 can afford, while the output stays a realistic timed route.
- **Implementation effort:** M–L: shortest-path differencing, PM/GRR, Furness/IPF, simulated-moments calibrator, shared router; BPR optional.
- **Main risk / failure mode:** Identifiability (several θ explain the same moments) and Geolife's mixed modes (walking, cycling, bus) break a single car-like cost model; fit time per generator (17 per membership arm) must stay under about 20 s.

### Idea 4: Mobility programs: compile a user's month into a tiny program, randomise the program, execute it on the public map (the unusual one)
- **One-sentence pitch:** Each device compresses its data into a fixed-shape program in a public grammar (anchors, routines, style) with coarse translation-invariant slots; LDP acts on the program, and the server synthesises coherent users by executing sampled programs on the road graph.
- **What each user computes locally:** Grammar: HOME zone h (16); WORK as an offset from home: distance bin δ (5) × compass sector φ (8); COMMUTE: days/week (4), leave hour t₁ (6), away duration (4); ERRAND: trips/week (4), radius (4), time of day (4); STYLE: router profile p (shortest / fastest / avoid-major), speed class s (slow / typical / fast). The device fits the program deterministically (home = modal night start zone, work = modal morning destination, and so on) at no privacy cost: one tuple from about 10⁷ programs, 11 slots. n≈180 grammar: four slots (home quadrant, δ, t₁, p).
- **What is randomized and how:** Mode A (n≈180): slot sampling, GRR_ε on one slot. Mode B (n≈10k): prefix-extending heavy-hitter protocol (PEM, Wang et al. 2018): users are publicly split into four groups, group g reports OLH_ε of the first g slot blocks of its program, and the server extends only frequent prefixes. One ε-LDP report per user either way.
- **What the server does:** Mode A: slot marginals shrunk toward public priors (gravity for δ given h, uniform φ). Mode B: frequent complete programs ("archetypes") with frequencies plus small pairwise tables for adjacent slots (OUE); the remaining mass by Gibbs sampling over the estimated conditionals (Farooq et al. 2013).
- **How a synthetic trajectory is generated:** Sample a program and execute a synthetic week: home node in h by public residential-road density; work node nearest the (δ, φ) offset; H→W at t₁ (jittered) and W→H after the away bin, each routed on the directed graph by profile p (Dijkstra on length, length/maxspeed, or length × major-road penalty); errands H→random node within the radius→H; edge time = length/(s·maxspeed), s ∈ {0.5, 0.75, 1.0}, plus turn delays. Trips are emitted unlinked; every trip is a Dijkstra path, hence road-valid. `sequence_log_prob` is a documented surrogate: log P̂(zone of first edge) + log P̂(δ, φ bins of the endpoints) + log P̂(period) + log Σ_p P̂(p)·(Boltzmann-relaxed path likelihood under p), floored; the exact likelihood is a sum over programs.
- **Why it is user-level pure LDP:** The program is a deterministic function of the whole month; the report is GRR/OLH of one slot or prefix chosen by a public coin, so the one-report lemma gives ratio ≤ e^ε between any two months. Subtle: bins and groups are data-independent; trip counts appear only as binned slots of a fixed-shape program; in mode B the adaptive candidate set uses only earlier, disjoint groups.
- **Expected behaviour at n~180 vs n~10,000:** n≈180: four slots × ≈45 users, GRR std 0.07–0.08 at ε = 2: a mix of home quadrant, commute length, leave time and routing style, the rest from priors. n≈10k: all 11 marginals (std 0.02–0.04); with four prefix groups of 2,500 users, archetypes with frequency ≳ 5 % are found at ε = 2 (≳ 10 % at ε = 1), so archetypes are coarse ("north-west, 5–10 km, leaves 7–8, fastest route"); pairwise tables only for ≤ 20-cell pairs.
- **Closest existing work and what differs:** Activity-based demand models (MATSim, ActivitySim), IPF/Gibbs population synthesis (Beckman et al. 1996; Farooq et al. 2013), central-DP deep generative travel diaries (Badu-Marfo et al.), LDP string heavy hitters (PEM, Apple SFP), Bayesian program learning. I know of no LDP scheme that randomises a compiled per-user mobility program and regenerates by executing it. Difference from every neighbour: the synthesis unit is a coherent user with recurrence and round trips, and relative slots (offsets, bins) make n≈180 feasible at all.
- **Implementation effort:** M: program compiler, GRR/OLH + PEM, Gibbs sampler, executor with three Dijkstra profiles.
- **Main risk / failure mode:** Misspecification: Geolife users (researchers, mixed modes, about nine matched train trips each) do not follow a commute template, so programs are noisy and archetype mass is small; the surrogate log-probability may behave oddly in LiRA; current metrics score single trajectories, so per-user coherence, the main asset, is not rewarded yet.

### Ranking
1. **Idea 3 (revealed-preference calibrated simulator)** is the best fit for the gap: user-level LDP by construction, realistic road-valid routes with physically motivated timing, and a parameter count (≤ 6 at n≈180) that is honest about the scale constraint while scaling naturally to T-Drive.
2. **Idea 4 (mobility programs)** is the most original and the only one producing coherent synthetic users; it carries higher misspecification risk on Geolife and a surrogate likelihood, so it is the stronger thesis story but the weaker benchmark bet.
3. **Idea 2 (part-of-speech n-grams)** is the cheapest to build and score with the cleanest privacy story, but it cannot place trips; best as the route-style module inside Idea 3 or 4.
4. **Idea 1 (spectral field)** has the most elegant degradation knob, but at n≈180 it reduces to a smooth density with no route realism; its value appears at n≈10,000.
5. Composition note: Ideas 1 (where and when) and 3 (how and how fast) share the router and could merge into one mechanism with two slot families, keeping the one-report guarantee.
